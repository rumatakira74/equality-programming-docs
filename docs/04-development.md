# 4. Процесс разработки

Разработку ведёт CLI-агент (Vibe) по этапам; владелец принимает решения. Все артефакты процесса живут в основном репозитории.

## Источники процесса

| Файл (в equality-trust-networks) | Назначение |
|----------------------------------|-----------|
| `docs/development-plan.md` | План этапов; после каждого этапа помечается выполненным с ветками и SHA |
| `prompts/stage-N-prompt.md` | Промпт этапа для CLI-агента; коммитится до запуска этапа |
| `reports/REPORT-STAGE-N.md` | Отчёт по этапу (что сделано, находки, метрики, артефакты) |
| `QUESTIONS.md` | Реестр вопросов (№1, №2…). Решение принимает только владелец |
| `docs/KNOWLEDGE.md` + `docs/KNOWLEDGE-1..5.md` | Спецификация: титул/оглавление + части 1–5 по границам разделов; версия поднимается только авторизованными пунктами changelog |

## Правило вопросов

Вопросы, требующие решения владельца (трейдоффы, семантика, параметры), фиксируются в `QUESTIONS.md` со статусом PENDING и вариантами. **Не додумывать**: если семантика не определена — реализуется минимальная безопасная версия, вопрос фиксируется, решение не блокирует остальные пункты мандата.

## Ветвление и merge

- Каждый этап — **отдельная ветка от свежего `main`** (`stage<N>-<тема>`).
- Пуш ветки и merge в `main` — **только после подтверждения владельца**.
- После merge в main — удаление remote-ветки (удаляет владелец в GUI; CLI-агент удаление веток не исполняет).
- При конфликте с параллельными правками промпта — приоритет у версии `main`.
- Владелец выполняет git-операции в GUI (GittyUp): называть только ветки и целевые SHA, консольные команды ему не давать.

## Чекпоинты сессии CLI (обязательные правила)

- **Промежуточный коммит раз в ~30 минут** работы с номером сессии в сообщении (за час агент успевает израсходовать ~1M токенов — потеря часа недопустима).
- **После любого рестарта сессии** (`vibe --continue` и т.п.) — сначала сверка живого состояния с последним коммитом, и только потом действия. Компaction-свод может быть устаревшим: известный инцидент — продолжение повторило уже завершённую и закоммиченную эру симуляции.
- Состав промежуточных коммитов: WIP-код и прогресс — да; бинарники, артефакты сборки, scratch — нет. **Финальный коммит этапа — чистое рабочее дерево.**

## Гигиена репозитория

- Не коммитить: бинарники (даже в корень — `.gitignore` закрывает известные паттерны), артефакты сборки Flutter/Gradle, тяжёлые scratch-файлы. Скриншоты и данные прогонов — в `reports/`, следить за весом (файлы >1 МБ — только легитимные данные, например metrics.csv).
- После прогона — **уборка процессов**: остановка Gradle-демонов, завершение `tnp-node`/`tnp-testnet`/`qemu`/`java`/`go`; перед новым прогоном проверять `pgrep`. Агент за собой java/go не закрывает сам — пункт включается в каждый промпт с прогонами.
- Сдвиг системных часов хоста для ускоренных флотов: выданный sudoers-грант используется по задаче; по завершении — вернуть часы (хост + эмуляторы), включить timesyncd, **удалить sudoers-правило**.
- Пуш по правилу 3 промпта: коммиты накапливаются локально, пуш — по подтверждению.

## Стиль кода

- Комментарии в коде — на русском.
- Имена файлов и идентификаторы — английские.
- Локальные каталоги: `~/projects/equality-trust-networks`, `~/projects/anti-farm-simulation`.
- Приватные данные в репозитории не появляются.

## Обновление документации (по итогам каждого этапа)

1. `docs/KNOWLEDGE.md` (титул и оглавление) и части `docs/KNOWLEDGE-1..5.md` — новая версия спеки только по авторизованным пунктам (changelog-заголовок с датой).
2. `docs/development-plan.md` — этап ✅, ветки, SHA, находки.
3. `prompts/stage-(N+1)-prompt.md` — промпт следующего этапа.
4. Этот репозиторий (`equality-programming-docs`) — при изменениях архитектуры/процесса; `equality-user-docs` — при изменениях, видимых пользователю.
